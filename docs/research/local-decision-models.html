A 421M Model, and the 40 Lines of BM25 That Beat It

September 2026 · 8 experiments, one day, one Mac · partial — published while open · revised after independent review

Every aura-distill session reads a knowledge index before doing any work. The turn that does it costs 21,247 tokens — the largest fixed cost of a session, and four to five times what this project last published for the same index. The obvious fix was a small local judgment model. The obvious fix lost, to a zero-model control that fits in 29 MB. What it lost to, and the two places it did not, are more useful than a win would have been.

The constant everything hangs on

The measurement is cache_creation_input_tokens on the message whose input carries the SPINE.md tool result, across four real headless cells. The four agree to within 16 tokens. That counter covers the whole turn — the tool call, the tool result, the assistant content around it — not the file in isolation. It is the right number for “what does this mechanism remove”, and the wrong number to divide by file size.

The index grew, and nobody was watching the number

Against the July figure the index file is four to five times larger. The driver is not entry count — 59 to 65 entries is +10%. It is verbosity per entry: 61 tokens per entry then, 191 now, with a p90 of 474 and a single entry at 841. Index cost scales with how much gets written per line, and that is the number to watch.

Correction: the first version of this page said “2.3× under-documented” against a ~9k figure. That figure was never published by this project — it came from a different repository’s notes. An independent review of the pull request caught it. The comparison above uses this project’s own published measurement, and the story it tells — an index that grew — is a different and better one than a mis-measurement.

The zero-model control, which was supposed to be a formality

Before testing a model, we tested nothing: pure-Python BM25 over a 30-query evaluation set, in two tiers. Easy queries name a noun that also appears in the index line; hard queries announce the action in the user's own words with the index's distinctive nouns deliberately avoided (“my gaming crashes are back”). Eight arms, all declared before scoring, none re-tuned after.

Three findings, none of which needed a model

The index text is a worse retrieval key than the file content — 33 points on the hard tier. An index line is written to tell an agent when to read a file; that is not the same as describing what is in it.

A title-only index collapses (hard tier 0.27 → 0.13). Direct evidence against shortening the index to save tokens.

Rank fusion works; score fusion does not. Normalised max() blending added exactly zero, because BM25 scores from a 745-character document and a 6,000-character one are not on the same scale. Reciprocal-rank fusion never compares them.

Hit rate 3/3 across all three cells; the table counts two because only the warm cells are token-comparable. No stray reads, both arms read the same two files. Cache creation fell by 21,232 tokens against the measured index-read turn of 21,247. These are not independent measurements — both are the same cache-block accounting of the same turn, so the agreement is arithmetic, not corroboration. What it establishes is that the mechanism removes essentially all of that turn’s cost and adds nothing unexpected.

The prediction that was wrong

The expected-value model credited this mechanism with zero saved round trips: the agent still chooses, still reads. It saved one anyway. Turns went 5 → 3 because once the index read was gone, the agent read both candidate files in a single turn. It reorganised its own tool use in response to the change, and most of the wall-clock win came from that. Expected-value models of agent behaviour do not predict this class of effect.

The laya-yn failure generalises past this model: 65 independent yes/no questions produce 65 probabilities that were never compared with each other, so they are not on a common scale and ranking by them is close to meaningless. Any pipeline that scores N candidates with N independent calls and then sorts by the score has this bug, and it does not announce itself — the numbers look like confidences.

The ceiling is about 20 options, and it is a cliff rather than a slope. It tracks tokens per label, not the option count: 8 tokens still works, 5 does not. Sets of 45 and 65 score identically because both clamp to a 4-token floor — the labels are equally shredded, so adding twenty more changes nothing.

Cascading does not rescue it. Projecting a two-level tree from the measured per-level accuracies gives 0.652 at best (8 groups × 9 members); the one real cascade measured came in at 0.400. Two 80% steps make a 64% pipeline, and a wrong group at level one cannot be recovered at level two. Free BM25 remains at 0.867.

Semantics are not doing the work at these label lengths. Hand-written prose, its twelve highest-IDF terms with no grammar, and the bare file path are indistinguishable at every size — no gap exceeds three topics. The file path alone performs as well as the carefully written index description.

Where the model wins: judging one candidate

The routing verdict was weak on its own, because ranking 65 files from a short request is high-cardinality retrieval — BM25's home ground, not a classifier's. So the model was given the shape it is built for: two options, rich state, one judgment. Given the request and a candidate file's content: does this file answer it? That is precisely the question no zero-model signal can answer.

The first attempt said it rubber-stamps everything — specificity 0.100. That was nearly published as a second clean negative. The confound: the model sees roughly 700 characters of state, and every knowledge file opens with YAML front-matter, so it was being asked to judge boilerplate that looks identical across all 65 files.

The finding that outranks the model choice

Changing only how a candidate is described — same model, same items, same prompt — moves balanced accuracy from 0.600 to 0.750. That swing is larger than the entire distance between the model and BM25 anywhere in this programme. The data structure, not the model, is the dominant variable.

And the index line is the single most discriminative input available, beating the file's own content — the inverse of the retrieval result, where file bodies beat index lines by 33 points. The two do not conflict. Lexical matching wants volume; a judgment model with a 512-token window wants density.

The mechanism underneath every result

One sentence that explains all eight experiments

When labels are compressed to fit the option budget, the model stops doing semantics and starts doing keyword matching — which is what BM25 already does better, in 29 MB and 9–390× faster depending on the arm (43.8 ms, 238 ms and 1,895 ms against BM25’s 4.85 ms).

In a choice question every option shares a 192-token head budget. At ten options each label gets 17 tokens; at sixty-five, four. A median index line is 133 tokens, so 1.5% of the index could ever fit. The routing experiments did not measure whether the model can use the index — they measured a model that was never given it.

At eight to thirty-five tokens per label there is no room for meaning, only for terms, and the model degenerates into an expensive and worse BM25. It earns its weights only where it has room to read: one candidate, a few hundred tokens of real content, a yes/no judgment.

The design consequence is concrete: an index shaped for a decision model must not be a category taxonomy. Not sixty-five options, not twenty, not a five-by-thirteen tree. Cheap retrieval proposes; the model judges candidates one at a time, with the budget spent on content rather than split across labels.

The distillation side, killed by arithmetic

The second hypothesis was that most transcript turns carry no durable signal, so a cheap local classifier could cut what the extraction stage reads. Before building it: where does transcript volume actually live? Across nine real sessions, 1,903,214 characters — excluding the session that ran the analysis, which is itself one of the heaviest tool users on the machine and would make the result circular and unstable:

ComponentShare
Tool results75.4%
Tool call inputs17.5%
User text3.5%
Assistant text3.4%
Assistant thinking0.2%

About 93% of a transcript is tool traffic. A classifier that judges user turns is aimed at 3.5% of the volume, so even a perfect one cannot save more than that. The experiment was not worth its own design.

What replaces it needs no model: head-truncating tool traffic cuts 72% of the transcript at a 1,000-character cap, 79% at 500, 86% at 200. That is a knob, not a free win — a command that failed with a specific error is exactly what distillation should catch, and that error is often not in the first 500 characters. The measurable next step is an attribution study: trace evidence-origin knowledge entries back to their transcript turns and see how many cite tool output.

The uncomfortable part

Every item on that list came from measuring the existing system, not from adding anything to it. The most valuable single act of the day was discovering that a documented constant was wrong by a factor of 2.3.

Limitations, stated plainly

The evaluation set is self-written. Thirty queries, composed by the same agent that ran the experiments, because this machine held only nine sessions and twenty-eight user turns — too few to mine. Ground truth is one agent's reading of the index. Treat the ordering of arms as the result and the absolute numbers as provisional. The winning router is pre-registered for a held-out test against mined real queries, and is not to be re-tuned first.

Small n throughout. Thirty routing queries means one topic is worth 3.3 points, so gaps under ten points are noise. The gate results rest on ninety items. The end-to-end confirmation is two warm cells on one topic: its token accounting is deterministic and trustworthy, its wall-clock is indicative only.

One model, one prompt family. Four formulations were tried, not searched. A different small model, a fine-tune, or a longer context window would change the picture — particularly the 512-token window, which caused the front-matter confound and caps every option budget here.

The model arm depends on the zero-model arm. The passage handed to the gate is selected by BM25, so “the model configuration” is really a hybrid. There is no arm in which the model stands alone and wins.

Three corrections were made during the work, and all three were caught by measuring rather than by reasoning harder: a misread cumulative swap counter, a peak-memory estimate wrong by 2×, and a verdict that was an artifact of feeding the model YAML front-matter. The last one had already been written up before the follow-up experiment overturned it.
