# Files-only memory redesign

Discovery deliverable for [#75](https://github.com/tomacco/aura-distill/issues/75), part of program [#74](https://github.com/tomacco/aura-distill/issues/74). Status: **proposed**, revised after an adversarial clean-context review (section 9). Implementation is [#78](https://github.com/tomacco/aura-distill/issues/78); lifecycle is [#73](https://github.com/tomacco/aura-distill/issues/73); thin-index enforcement is [#41](https://github.com/tomacco/aura-distill/issues/41); read batching is [#64](https://github.com/tomacco/aura-distill/issues/64).

The problem in one line: the knowledge base only grows, every limit ends in "ask the user", and the one file loaded on every session start has become a digest instead of an index. This document decides the file layout, the budgets, the lifecycle policy, the retrieval protocol, the migration path and the honest guarantees of an edition that runs on files plus the harness the user already has. No new executable, daemon, service, connector, account or network dependency.

## 2. Decisions

### D1. Budgets are bytes and lines together; the first cap hit binds; checked at write time

The SPINE gets a byte budget in addition to its line budget, and each entry gets its own byte cap. A distillation may not finish with the SPINE over budget: the same run must shorten entries. "Flag" is no longer a terminal state for the index.

| Surface | Hard cap | Compact at | Note |
|---|---|---|---|
| `SPINE.md` | 80 lines and 16,000 bytes | 60 lines or 12,000 bytes | 12 KB is F3's implied ceiling; 16 KB (~4K tokens) is 30% headroom |
| One SPINE entry | 400 bytes | 200 bytes | An entry is its `- [` line **plus any wrapped continuation lines**. 400 B is the ceiling for any one entry; 200 B is the floor target when the **file** is over budget, and 80 entries at 200 B fit the 16 KB file cap by construction |
| One tier-2 file | 60 lines and 6,000 bytes | 45 lines or 4,500 bytes | Keeps the existing line cap and adds the byte cap that makes it meaningful |

**The per-entry and per-file caps are reconciled by the compact-at size, not by the ceiling.** F15 shows why the ceiling alone is not enough: 65 entries each cut to 400 B still make ~26 KB, over the 16 KB file cap, while 65 entries at ~240 B fit. So SPINE compaction cuts every entry over the 400 B ceiling to within it and then, while the file is over its byte cap, shortens entries **longest first toward 200 B** until the file fits; an entry may stay between 200 and 400 B while the file has room (the fixture's merged testing line is 276 B in a 1.5 KB SPINE). 80 lines × 200 B = 16,000 B, so once every entry is at its compact-at size the byte cap can be exceeded only by the header and headings, and the line reclamation below takes over. The third store in F15 (~8 KB, largest entry 385 B) shows a thin index is what users already write when nothing inflates it.

These numbers are **provisional**. The line caps are the shipped ones; the byte caps are set from F3 and headroom, not measured. #62 measures the redesigned files edition and owns adjustments; the checker takes every cap as a parameter.

**Where the old SPINE wording goes.** The hook of an over-cap entry is not evidence, it is index detail that may contain principles nobody wrote elsewhere (the fixture's original testing entry names three rules absent from the file). When an entry is compacted, the **entire original hook text** (everything after the pointer, exactly as the ledger would record it as `spine-entry`) is appended verbatim to the target tier-2 file under `## Index detail (moved from SPINE <date>)`, and the new short entry is written fresh. Not the removed fragment: the whole hook, so that the migration oracle (section 5, C4: "every original hook survives as a substring") holds and the next distillation of that domain can fold the complete text into proper principles. It never goes to the evidence twin, which retrieval does not read. Order of operations: append, re-check the target against its own caps, split if the append pushed it over. (The fixture's `craft/testing-2.md` shows the split mechanics; in the fixture the append alone would not have crossed the cap, the split is there so the split-family logic has a positive case.) Entry hooks keep the **distinctive nouns** that make retrieval fire (project names, tool names, error strings); compression removes explanation, never triggers.

**Line reclamation.** Migration adds SPINE lines (the catalog line, one per split child) and a store that already sits at the 80-line cap (the profile in F3 does) would never terminate within budget. The plan therefore reclaims lines mechanically, in this order, until the SPINE fits: (1) a split child never gets its own line, it shares the parent's as a second pointer (`- [A](a.md) + [A, continued](a-2.md) — hook`; multi-pointer entries are the shipped shape for related files); (2) blank lines are dropped (headings stay, they are navigation); (3) entries whose targets sit in the same tier directory and share a topic are merged into one multi-pointer line, which is the existing spine-compaction rule made mechanical, and each merged entry's original hook is appended to its own target file under `## Index detail`, exactly as for an over-cap entry, so no hook is lost; (4) if the SPINE still does not fit, the plan **refuses** with the named reason, lists the eligible `projects/` files the lifecycle policy would archive and the entries a user could pin or merge by hand, and changes nothing. A hook is "everything after the **leading pointer group**" (one or more pointers at the start of the entry, joined by ` + `), minus the separating dash, so a multi-pointer entry has one hook shared by its targets; the checker, the ledger and the catalog all use that definition.

**Multi-pointer lines and the lifecycle.** Archiving one target of a merged line removes **that pointer only** (`+ [B](b.md)`), leaves the line and its hook in place, and the ledger saves a **derived single-pointer entry** (`- [B](b.md) — hook`) as `spine-entry`; the line is removed entirely only when its last target is archived. Restore re-inserts the pointer into the merged line if that line still exists, otherwise re-adds the derived entry. A **split family** (parent plus `split_from` children) is one lifecycle unit: archived and restored together, one ledger line per file, and never split across active and archive (a child left active blocks the parent, a parent left active blocks the child).

**A new learning when the SPINE is full.** An ordinary distillation never drops a learning and never asks about the index. It encodes the learning into a tier-2 file first. If an existing file covers the domain, the learning goes there and needs no new SPINE line (the entry's hook may be refreshed within 200 B). If it would need a new file and the SPINE has no room after shortening entries and the reclamation steps (1) to (3) above, it is instead appended as a new section to the closest existing file of the same tier; if that pushes the file over its cap, the file splits and the child shares the parent's line (step 1). The report names the file it went to. The refusal in step (4) belongs to migration only.

**Oversize files.** Splitting is the **primary** remedy for an over-cap tier file, not the evidence twin (F15: moving dated observations out fixes 3 of 56 over-cap files). A tier-2 file that legitimately needs more than the cap (for example a file of twenty protected `[NON-NEGOTIABLE]` lines) is **split**: `craft/x.md` keeps the first part, `craft/x-2.md` carries the rest with frontmatter `split_from: craft/x.md`, both are pointed to from the parent's SPINE line, and the checker treats the split family as one unit for conservation. Splitting relocates wording verbatim, so F7 is respected. A file that cannot be split without breaking one atomic block may carry `oversize: <reason>` in frontmatter; it is then exempt from the byte cap and listed as such in the catalog, and the exemption is reported at every run.

Client rules files (F1) are a fixed recurring cost outside this design; the always-on block is governed by `distill-process.md` Step 3c and is not changed here.

### D2. Evidence moves to a parallel tree; the principle file keeps only the principle

New directory `evidence/`, mirroring the tier tree: `craft/review-protocol.md` pairs with `evidence/craft/review-protocol.md`. The evidence file is **append-only**, never compacted, never listed in the SPINE, and holds the dated record: confirmations, corrections, observations, superseded findings, session pointers. The principle file keeps the principle, its `confidence:` line with counts, its `last_validated:` date and a one-line citation ("Evidence: 2026-04-18 to 2026-08-30 in `evidence/craft/testing.md`").

Format of an evidence file (an **entry** is a line beginning with `- `):

```markdown
---
evidence_for: craft/review-protocol.md
---
- 2026-07-12 confirm: reviewer caught a numeric-range crash both twins missed (PR #39)
- 2026-08-10 correct: relayed root-cause was wrong; observation right, diagnosis reproduced
```

`evidence_for` names the tier path the twin belongs to and is that file's **identity for the files-only edition**; it always equals the twin's own path minus `evidence/` (the checker asserts it), and it does not change when the file is archived (the archived copy lives at `archive/<same path>`). An evidence file whose `evidence_for` names neither an active nor an archived file is an orphan and fails the checker. Track B (#82) introduces stable IDs; until then a path plus the no-collision rule in D3 is the reference.

Protected wording comes in two shapes and both stay in the principle file. A protected **bullet** and its **indented continuation lines** (`confidence:`, `origin:`, `Why:`) travel together. A protected **section**, a heading that carries the marker (`## [DIRECTIVE 2026-08-02] Title`, the shape the shipped process file uses for `## [DEPRECATED]` and `## [CORRECTED]`), runs to the next heading of equal or higher level and travels as a whole, including its non-indented bullets. The checker protects both shapes. When a section's dated observations move to the twin, the section heading stays in the principle file (or travels with them if the section is emptied); either way every line survives somewhere, which is what the conservation check demands. A protected marker is any bracket that **starts** with `NON-NEGOTIABLE` or `DIRECTIVE`, so the dated forms real stores carry (`[NON-NEGOTIABLE 2026-05-02]`, `[DIRECTIVE 2026-08-02]`, the shipped `[UPDATED date]` convention) count; the pattern is `\[(NON-NEGOTIABLE|DIRECTIVE)[^]]*\]` everywhere it is used (checker, lifecycle exemption, runtime self-check).

Consequences: evidence no longer competes with principles for the cap (F6 dissolves), validation history stays intact and cheap, and "why do we believe this?" has a place to look. The twin is **not** what makes the tier-2 cap reachable: F15 measures dated observations at ~6.5% of tier-file lines, so most over-cap files reach the cap by splitting (D1). Evidence is knowledge and belongs to the shared sync set (F11). Old clients never read `evidence/`; their orphan scan globs only tier directories, so they do not misreport evidence files.

### D3. Archive is a byte-identical move, recorded in a synced ledger, never a rewrite

Archiving `projects/atlas.md` means `mv projects/atlas.md archive/projects/atlas.md`. Nothing inside the file changes, so the move is verifiable by checksum and reversible by one move back. Its evidence file stays where it is.

Provenance is written **at move time** to `archive/LEDGER.md`, an append-only, synced file with one line per move or restore:

```markdown
- 2026-09-11 archive | from: projects/atlas.md | to: archive/projects/atlas.md | sha256: 12c18385… | reason: past threshold, no validation observed | spine-entry: - [Atlas](projects/atlas.md) — Atlas data-platform migration …
```

The ledger line carries everything a restore or a second machine needs: the checksum, the reason, and the **full removed SPINE line**, so restore re-adds the entry that was removed (rewritten within the D1 entry cap if it predates compaction, with the entire saved hook going to the restored file's `## Index detail`) and nothing has to be invented. Restore-on-request also replaces the old `recall_count` promotion rule: when a miss resolves to an archived file the user then works on, the next distillation restores it. The catalog (D4) derives its archived rows from the ledger; a rebuilt catalog therefore never loses provenance, and a machine that receives the archive through sync receives the ledger with it.

**Ledger events.** Four event kinds, one line each, always appended, never edited:

| Event | Line shape | Written |
|---|---|---|
| `archive` | `- DATE archive \| from: X \| to: archive/X \| sha256: H \| reason: R \| spine-entry: LINE` | before the move |
| `restore` | `- DATE restore \| from: archive/X \| to: X \| sha256: H \| reason: R` | before the move back (`reason: user request`, or `reason: revert <manifest>` when a migration or gc plan is reverted, one line per reversed move) |
| `restore (modified)` | same shape, event text `restore (modified)`, `sha256:` = the checksum actually observed | when the archived file no longer matches its `archive` checksum |
| `move never completed` | `- DATE restore \| from: archive/X \| to: X \| reason: move never completed` | by a recovery run that finds an `archive` line whose move did not happen |

These are the only event words. A ledger line whose event is anything else (`purge`, a typo), or that does not start with a date, is an error the checker and the runtime self-check report loudly; it is never skipped. Dates are written as UTC timestamps (`2026-09-11T10:31:00Z`) by new clients; date-only lines (older runs, the fixture) remain valid. Every path on a ledger line obeys D10, and `to:` is exactly `archive/` + `from:` for `archive` and the reverse for `restore`.

**State is the last event per path.** For every path X, the newest line whose `to:` or `from:` names `archive/X` decides: last event `archive` means X is archived (`archive/X` exists, X does not); any `restore` event means X is active (X exists, `archive/X` does not). A ledger that disagrees with the tree is an inconsistency the checker reports (C2), the migration self-check catches before clearing `PENDING`, and a recovery run repairs by completing the move or appending a `move never completed` line. Because the ledger is written before the move, a crash in that window is exactly this case and is repaired, not hidden.

**Byte identity means bytes.** Checksums and identity checks hash raw bytes; only line comparisons and counts ignore carriage returns. Consequently `archive/**` and `archive/LEDGER.md` must cross machines byte-exact: the sync protocol (#61) and any backup plugin must not normalise line endings for them. A git-backed backup with `autocrlf` on would break every ledger checksum on the receiving machine; D9 records this as a constraint on #61.

**Archived files are read-only for every client.** Validate-on-read and `recall_count` bumps do not apply under `archive/`; a session that reads an archived file on a miss changes nothing. Restore verifies the file against the ledger checksum; on mismatch it restores anyway, reports the difference, and appends a `restore (modified)` ledger line.

**Field syntax (ledger and catalog).** Fields are separated by ` | ` and parsed **from the left**; each key appears once and `spine-entry:` is the last field of an `archive` line. A literal `|` inside a free-text field (the saved SPINE line or hook, `reason:`, the catalog's scope text) is written `\|`, the markdown-table escape, and unescaped when read (restore re-adds the SPINE line with plain `|`). An unescaped ` | ` inside free text, or a repeated key, is an error: otherwise a hook containing `| to: archive/projects/comet.md` would forge a field.

**No collision.** A path may not exist both as `X` and `archive/X`. A project that comes back is **restored**, not re-created; gc and the distiller refuse to write `projects/atlas.md` while `archive/projects/atlas.md` exists and report the collision. The checker enforces it.

**Legacy archives.** Files produced by the old rewrite-style compaction (F4, F5) have no ledger line. Real stores hold them flat under `archive/` and, mostly, in tier subfolders of it (`archive/projects/x.md`, F15). Legacy is **structural**, not a label: a file directly under `archive/` or anywhere under `archive/legacy/` is legacy, a file under `archive/<tier>/` never is, and the catalog's `legacy` label must agree with the path. Structural rather than ledger-derived on purpose: if "no ledger line" meant legacy, deleting a ledger line would silently turn a checksummed archive into an unchecked one; with the structural rule it is reported first (C2, Step 0 "pending adoption") and only an explicit `migrate-store` plan adopts it. That a deleted ledger line still looks exactly like an old-client archive is a named accepted risk (section 6). Migration therefore **adopts** every archive file that would otherwise be misread: each file under `archive/<tier>/` with **no ledger `archive` event at migration time**, and (at no extra cost) any file in an `archive/` folder nested inside a tier directory, is moved byte-identically to `archive/legacy/<its original store-relative path>` (`archive/projects/x.md` → `archive/legacy/archive/projects/x.md`; `craft/archive/y.md` → `archive/legacy/craft/archive/y.md`), listed in the plan like any other move and reversed by revert; no ledger line, because legacy files have none. Flat files stay where they are. After migration every file under `archive/<tier>/` has a ledger event and none sits in an `archive/` folder inside a tier directory (C2). Legacy files are kept as they are, never deleted (Tier 3's cardinal rule), and never checked for identity against a source that no longer exists; they are checked for identity against their own pre-migration copy (for an adopted file, the file at its original path).

### D4. A complete catalog replaces "the SPINE mentions it"

New file `CATALOG.md` at the store root, **not auto-loaded**, rebuilt by the distiller at the end of every run. One line per file under `craft/ ops/ profile/ projects/ feedback/ archive/ evidence/`, sorted by path, grouped by status:

```markdown
# Knowledge catalog
<!-- Complete inventory, rebuilt by /distill. Not loaded at session start. rebuilt: 2026-09-11T10:31:00Z -->
## active
- craft/testing.md | Testing philosophy for Noor's services … | validated 2026-08-30
- projects/comet.md | Comet billing reconciliation — on hold, retention rules | validated 2026-05-06 | pinned
## archived
- archive/projects/atlas.md | Atlas data-platform migration … | archived 2026-09-11 | reason: past threshold, no validation observed | from projects/atlas.md | hook: Atlas data-platform migration from the legacy warehouse …
- archive/old-warehouse-notes.md | Superseded warehouse notes | legacy
## evidence
- evidence/craft/testing.md | for craft/testing.md | 30 entries
```

Every field is derived: `scope:` from frontmatter; `validated DATE` = the newest of every date stamp in the file (frontmatter `last_validated`, `last_updated`, per-principle `last_validated`); `pinned` from `lifecycle: pinned`; archived rows from the ledger's last event per path (the `hook:` field is the removed SPINE line's hook text, which is what a miss search needs to match); evidence counts by counting `- ` lines; free text follows D3's field syntax (`\|` for a literal pipe). The rebuild is therefore mechanical and the checker (C2) asserts the catalog equals the tree: presence of every file, evidence counts, the `pinned` flag, the `validated` date, `from` and `hook` on archived rows with the hook equal to the ledger's `spine-entry` hook, ledger last-event agreement with the tree, and a `rebuilt:` stamp no older than the newest ledger event (full UTC timestamps compared when both carry one; see D5 step 4 for date-only stamps). Every path in the catalog obeys D10.

The SPINE carries exactly one fixed line pointing at the catalog. No list of archived names ever enters the SPINE; this supersedes the shared "Archived projects: a, b, c" line proposed in #73.

### D5. Scoped misses: the catalog bounds what "not found" means

Retrieval protocol on a miss, added to `distill-monitor.md`:

1. The request **refers back to earlier knowledge** (a named project, person or system the user expects you to know, "what did we decide", "last time", "as before") and no SPINE hook matches it. Only then search `CATALOG.md` for the topic's distinctive words. A new task that does not appeal to prior knowledge reads no catalog; the catalog is a miss resolver, not a second index (archived rows carry the original hook, so a project archived last month still matches on its own nouns).
2. An archived match: read it, state "found in the archive (archived on DATE, reason R)". Read-only; no stamps change (D3).
3. No catalog match: say **"No SPINE entry or catalog line (rebuilt DATE) names X. It may still sit inside a broader file. This is not proof X was never distilled."** Never convert a miss into "we never distilled X".
4. The catalog is **stale** when any catalog line points at a missing file, when a file under the tier directories, `archive/` or `evidence/` has no catalog line, or when the newest ledger event is later than the catalog's `rebuilt:` stamp. The comparison uses full UTC timestamps when both sides carry one; when either side is date-only it compares dates, and a move made later on the same day as the rebuild is then **not detected** (a named limitation of date-only stamps, which is why new clients write timestamps). All three are content checks that work after a sync, a copy or a checkout (modification times are not preserved by those and are never used). A stale catalog is named as such in the answer.

This is the files-only shape of #66. The model is instructed; nothing enforces the wording at runtime (section 6).

### D6. Required reading is declared, and reads are batched

Tier-2 files may declare `read_with:` in frontmatter as an **inline list** (`read_with: [ops/deploy.md, craft/testing.md]`; the block-list form is rejected by the checker so there is one shape to parse). `distill-monitor.md` gains two rules:

- After reading the SPINE, issue **all** matched tier-2 reads in one batch (parallel tool calls) when the client supports it; serialize only when a file's content decides what to read next.
- After that batch, read the union of their `read_with:` lists in one more batch. Depth is one; no transitive closure. A file that needs a deeper chain lists the deeper file directly.

A synced file may not `read_with` a path under `local/` (D9), and every `read_with` target obeys D10. Old arrow-style cross-references in prose stay as navigation hints. Which clients honour parallel tool calls is verified per client in #78.

### D7. Lifecycle: an enabled policy acts on eligible files without per-item questions

The policy is **opt-in** (release frame: a behaviour change ships as a knob). It is persisted in `{DISTILL_DIR}/.lifecycle` (`enabled` or `disabled`; absent means disabled), a local dotfile like `.token-saver`. When disabled, the distiller reports debt and asks nothing, which is strictly less noise than today.

When enabled, at Step 5 of every distillation and on the standalone invocation `/distill gc`:

| Rule | Detail |
|---|---|
| Activity stamp | The newest of: frontmatter `last_validated`, frontmatter `last_updated`, and every per-principle `last_validated` line in the file. A file with **no date stamp at all is ineligible** and reported |
| Eligible | A file under `projects/` whose activity stamp is older than its `staleness_threshold` (default 90 days) |
| Exempt | Frontmatter `lifecycle: pinned` (also echoed as the word "pinned" in the SPINE hook so old clients' staleness review sees it); any file carrying a `[NON-NEGOTIABLE]` marker (treated as pinned and reported as such, because a safety rule must stay in the retrieval path even when its project is quiet); any file outside `projects/` (craft, ops, profile, feedback keep ask-first, because a stale principle is not a finished project). Users pin before the first pass by adding `lifecycle: pinned` to a file; the policy is off by default and previews before applying, so there is always a run to read the plan and pin |
| Blocked | A file named in the `read_with:` of another **active tier-2 file** (a declared required read). The reason is recorded in `data/lifecycle.jsonl` and in the report; nothing moves |
| Referenced | A file whose path appears in the **prose** of another active tier-2 file (arrow references, F9). SPINE, CATALOG, evidence twins, the ledger and the file's own split family never count: they name every file by construction. A prose reference does **not** block (F15: 18 of 23 real project files are referenced, so blocking would leave the policy nearly inert); the move proceeds, the report lists each referrer, and a reader that follows the now-dangling reference checks `archive/<same path>` first (the same rule as a dangling SPINE pointer, section 4) and reads it read-only |
| Action | Ledger line first (D3, including the full SPINE entry), then the byte-identical move, then the SPINE entry removal, then the catalog rebuild. The report lists every move; a move of a file carrying `[DIRECTIVE…]` markers is listed with the marker count, and that report line is mandatory, not optional |
| Manifest | `data/lifecycle/<ts>.json` lists every planned move with its source sha256 and a per-move `done` flag; it is written before the first move. A later run that finds an unfinished manifest **verifies each remaining source against its recorded sha256** and completes only exact matches; a mismatch (for example a stub an old client re-created at the source path) stops the run and is reported. Reverting uses the ledger line to re-add the SPINE entry |
| Concurrency | gc runs under the `.status` lock, refreshes it after every move (F10's 5-minute staleness), and refuses to start while another unfinished manifest exists |
| Restore | `/distill restore <path>` appends a `restore` ledger line, moves the file back, checks the ledger checksum (restore anyway on mismatch, report it), re-adds the saved SPINE entry **subject to D1**: if the saved entry is over the entry cap (an entry archived during migration was saved before compaction), a fresh short entry is written and the entire saved hook is appended to the restored file under `## Index detail`, then the catalog is rebuilt. A restore never finishes with the SPINE over budget |
| Preview | `/distill gc --preview` prints the plan and changes nothing; `--apply` executes it. Preview is the default |

Demotion is not a claim that the project ended. Age alone never means that; the move only says "not validated within threshold, kept whole in cold storage, findable through the catalog". **Maintenance reads are exempt from validate-on-recall**: eligibility scans, migration and gc read files without bumping any stamp, otherwise a migration would reset every clock on the same day. Reads without validation stay unobserved and count as unknown, not as inactivity; that is why only `projects/` files are eligible and the threshold is per file.

`[DIRECTIVE]` markers do not block a move, because a move preserves wording verbatim (F7 forbids dropping or compressing, not relocating), and a directive-bearing project file is retrievable through D5 the next time its project comes up; the move is listed with its marker count in the report. `[NON-NEGOTIABLE]` markers exempt the file (row above): that is the one place where an archive would weaken a safety property rather than a budget, so it is not automated. **Directive applicability** (who issued it, whether it has expired) is preserved as the existing `origin: directive (who, when)` wording and is otherwise deferred to Track B (#82), see section 8.

### D10. Every path read from a synced file is contained

Synced files arrive from other machines and may be edited by hand, and several of their paths drive **automatic** reads and moves. Rule **D10 (contained paths)**: every path taken from a synced file — SPINE pointers, `read_with`, `split_from`, `evidence_for`, the ledger's `from:` and `to:`, and catalog paths — must

- be relative: not starting with `/`, `\`, a drive letter (`C:`) or `~`;
- contain no `..` or `.` segment, no empty segment and no backslash;
- resolve inside the store's tier directories, `archive/` or `evidence/` (a SPINE pointer may also name `CATALOG.md`); never `local/` (D9), never the store root's dotfiles or `data/`;
- not pass through a symlink: the store contains no symlinks.

Narrower shapes apply per field: `split_from` and `evidence_for` name a tier path, ledger `from:`/`to:` are a tier path and `archive/` + that path. A path that breaks D10 is an error reported with its source file; it is **never** read, moved, restored or followed. The #78 runtime enforces D10 **before any read or move** it performs on a synced path, in the Step 0 integrity check and in gc, restore and migrate-store; the checker enforces it in C2 and C3.

## 3. Migration of an existing store

Run once by the distiller as `/distill migrate-store`, under the `.status` lock. Preview is the default; `--apply` executes.

1. **Preview.** Write `data/migration/<ts>/PLAN.md`: the legacy adoptions (D3), proposed SPINE (every entry within D1 caps, with the wording each cut entry will append to its target file), the list of lines per tier-2 file that would move to its evidence twin, the lifecycle plan if `.lifecycle` is enabled, and the three budget numbers before and after. The plan also lists **every path it will create or move**. Nothing else changes.
2. **Backup.** On `--apply`, copy the **whole knowledge tree byte-exact** into `data/migration/<ts>/backup/`: `SPINE.md`, `CATALOG.md` if present, every tier directory, `evidence/**` and `archive/**` including `archive/LEDGER.md`. Then write `PENDING`. Only then edit.
3. **Apply, per file, marking each file `done` in the plan as it completes.** Adopt unledgered and nested legacy archives (D3). For each tier-2 file: append the planned lines to `evidence/<tier>/<name>.md`, then rewrite the principle file, then mark done. The append is **idempotent by count against the backup, never by presence**: for each planned line L, the twin must end with (count of L in the backed-up twin, 0 if none) + (count of L in this plan's append), and a resumed run appends only the missing difference. It therefore skips only lines **this same plan already wrote**; a line that already sat in the twin before migration, and also in the principle file, ends up twice, with its multiplicity intact. Rewrite the SPINE from the plan and append cut wording to the target files. Create `CATALOG.md`. Perform lifecycle moves only if enabled (D7 rules, ledger first). Run the lossless self-check (section 5) and, only if it passes, delete `PENDING` and write `DONE` with the three numbers.
4. **Interrupted.** A later run that finds `PENDING` offers two mechanical choices. **Finish**: resume at the first file not marked done (the count-based append makes a half-done file safe). **Revert**: append one `restore` ledger line (`reason: revert <manifest>`) per move being reversed, reverse every move listed in the plan, delete every path the plan created (the ledger is never deleted, only appended to), then copy `backup/` over the store, and **rebuild `CATALOG.md` from the reverted tree and the ledger as the last step** (after a repeated migration the backup predates the revert's `restore` lines, so a restored catalog would be stale). Both are copies, appends and deletions from the plan, not judgement.
5. **Repeated.** Running migration on a migrated store is a no-op plan (no entry over cap, no evidence lines left in principle files) **except for adoption**: an unledgered `archive/<tier>/` file that appeared since (an old client archived it, D8) is adopted to `archive/legacy/<original path>` exactly as in step 3, listed in the plan and reversible by revert. The plan says which of the two it is. The lossless check's "before" is always the backup this run took (step 2: the whole knowledge tree, so every archived file has its original there), which may itself be a migrated store with archives, a ledger and twins; an archived file then counts as preserved when it equals its own earlier archived copy, its original tier file, or its last ledger `archive` checksum (restored, edited and re-archived), and a split child created and archived with its family is covered through its parent.
6. **Manual edits.** Users may edit any file at any time. The next distillation re-validates budgets and rebuilds the catalog. A user-edited SPINE over budget is compacted like any other over-budget write; cut wording goes to the target file, never dropped.
7. **Line endings.** The harness strips carriage returns in line comparisons and counts and writes files with the line ending the file already had; byte counts and checksums are raw (D3).

Which lines are evidence is a **judgement the distiller makes** (dated observations, confirmation counts, session anecdotes, superseded findings). The migration therefore cannot be proven correct by the agent; it is proven **lossless** by a mechanical check: every non-blank line of every pre-migration tier-2 file **together with its pre-existing evidence twin** must appear, **as many times as it appeared in the two combined**, across its principle file, its evidence twin, its split children, or its archived copy. The count is over the combined multiset, so a duplicate collapsed into one copy fails. `tests/files-only/check-store.sh` is the **reference implementation** of that check and stays developer-side: it is not downloaded to users and the runtime never depends on it (#75's "no new end-user executable" holds). What the distiller runs before clearing `PENDING` is the **same invariants written as harness commands inside `distill-process.md`** by #78: `wc -c` or `(Get-Item).Length` for budgets (bytes, never `.Length` of a string, which counts UTF-16 characters and undercounts every em dash), `sha256sum` or `Get-FileHash` for identity, a sort-and-count comparison for line conservation, in a bash block and a PowerShell block. The invariants are deterministic; the agent's execution of them is best-effort (section 6). #78 proves the two command blocks agree with the reference script on the fixture before shipping (the `check-store.ps1` developer twin exists for that parity test only).

### Handoff notes for #78

- **D10 before every read or move.** Step 0, gc, restore and migrate-store validate every synced path (SPINE pointers, `read_with`, `split_from`, `evidence_for`, ledger `from:`/`to:`, catalog paths) against D10 before touching it, in both the bash and the PowerShell command blocks, and report the offending file instead of acting.
- **`recall_count` from old clients.** Old clients follow the shipped Tier 3 rule and bump `recall_count:` inside archived files on every read, so on a mixed-version store the raw ledger checksum routinely stops matching. Step 0 must tolerate that field: compare the archived file with its `recall_count:` frontmatter line removed against a normalised checksum. Preferred shape: new `archive` ledger lines carry an additional `sha256-norm:` (checksum with that line removed; additive, old lines lack it), Step 0 reports a mismatch confined to `recall_count` as drift rather than modification, and restore resets the field. The raw `sha256:` stays the identity for everything else. The new instructions also drop the Tier 3 bump (D3: archives are read-only).
- **Unknown ledger event words fail loudly** in the runtime self-check, as in the checker (D3).
- **Timestamps.** New ledger lines and the catalog's `rebuilt:` stamp are UTC timestamps (D5 step 4).
- **Legacy adoption** (D3): unledgered `archive/<tier>/` files, the real-store shape, and any `<tier>/**/archive/**` files move to `archive/legacy/<original path>` during migration; the old orphan scan must not mistake the nested ones for tier files in the meantime.
- **Split heuristics.** Splitting is the primary remedy for over-cap tier files (D1, F15); where to cut (by section, keeping protected sections whole) is a #78 heuristic, verified on the fixture.

## 5. Synthetic fixture and deterministic checks

`tests/files-only/store-before/` is a mature synthetic store for a fictional persona (Noor, platform engineer) that reproduces every diagnosed failure: SPINE entries over 400 bytes that carry principles found nowhere else, a tier-2 file over 60 lines because it holds 30 dated observations, two `projects/` files past threshold (one pinned), files with `[NON-NEGOTIABLE]` and `[DIRECTIVE]` wording, a legacy flat archive file, an unledgered `archive/projects/ember.md` in the shape real stores carry, an evidence-free file that must survive untouched. `tests/files-only/store-after/` is the same store after migration and one lifecycle pass with the policy enabled.

`tests/files-only/check-store.sh <store-dir> [--before <original-dir>]` asserts, deterministically and offline, ignoring carriage returns:

1. **C1** SPINE within D1 caps (lines, bytes, per-entry bytes, an entry measured with its wrapped continuation lines); one catalog line present.
2. **C2** Every SPINE pointer resolves; every active tier-2 file has a SPINE pointer on an entry line (`- [`, never a comment or prose); a catalog exists and lists every active, archived and evidence file with no line pointing at a missing file; each active row's `validated` date equals the file's newest stamp and its `pinned` flag equals `lifecycle: pinned`; evidence counts in the catalog equal the `- ` lines in each twin; every `evidence_for` names an active or archived file; no path exists both active and archived; for every path named in the ledger the last event agrees with the tree; every non-legacy archived file's last `archive` event carries its sha256; archived catalog rows carry `from` and a `hook` equal to the ledger's `spine-entry` hook; every ledger line starts with a date or timestamp and uses a known event word, with `to:` = `archive/` + `from:` (or the reverse for a restore); the catalog's `rebuilt:` stamp is not older than the newest ledger event (full timestamps when both carry one); ledger and catalog lines follow D3's field syntax (known keys, no repeated key, no unescaped ` | ` in free text); SPINE, catalog and ledger paths obey D10; the store contains no symlinks; no legacy archive remains inside a tier directory.
3. **C3** Every tier-2 file within D1 caps unless `oversize:`; `read_with` is an inline list whose targets obey D10, exist and are not under `local/`; `split_from` targets obey D10 and exist.
4. **C4** (with `--before`) Every non-blank line of every original tier-2 file **combined with its original evidence twin** appears **at least as many times** in the after store (principle file, evidence twin, split children, archived copy), and every line of an original twin also survives in that same twin; every protected bullet (dated forms included) **and its indented block** still exists in an active or archived file; every archived file that is not legacy is byte-identical (sha256) to its earlier archived copy or its original tier file, or, when it was legitimately edited after migration and before a later move (an Index detail appended, or restored, edited and re-archived), to its last ledger checksum, its original lines then being covered by conservation (a split child archived with its family is covered through its parent); every file that was under `archive/` before still exists there, every legacy file is byte-identical to its own pre-migration copy, and every archive file that had no ledger `archive` event before, and every nested legacy archive, was adopted byte-identically under `archive/legacy/`; a pinned file and any file carrying `[NON-NEGOTIABLE…]` were not moved; every original SPINE hook survives as a substring in `SPINE.md`, a tier file, an archived knowledge file or the catalog (never counting `data/`, evidence, or the ledger itself; for archived files the catalog row carries the hook by construction, so that case is guaranteed by the rebuild rather than tested independently).

The after store exercises a **split** (`craft/testing-2.md` with `split_from: craft/testing.md` carries the index detail cut from the SPINE) and a merged multi-pointer line (Beacon + Delta). `tests/files-only/run-files-only-tests.sh` asserts that `store-before` FAILS C1 to C3 with the named diagnosis reasons, that `store-after --before store-before` PASSES, also when `--before` is restricted to exactly the documented backup set (section 3 step 2) (including the adoption of `archive/projects/ember.md`, which has no ledger line in `store-before`), that seventy-nine tamper cases are each caught with their named reason, and that ten positive cases pass (a repeated migration adopting an old-client archive, an `oversize:` exemption, two restores for the `restore` and `restore (modified)` events, archiving one target of a merged line by pointer removal, a pre-existing duplicate preserved across principle file and twin, a timestamped catalog rebuilt after a same-day event, a re-archive after restore and edit with a migrated store as `--before`, an adopted nested legacy archive, an escaped `\|` in a ledger reason and hook). **Coverage claim, stated exactly:** every `fail` branch in `check-store.sh` has at least one tamper case whose expected reason names it, except the symlink case, which is skipped on a filesystem that cannot create symlinks (Windows Git Bash without developer mode); the runner lists each case by name. It runs in CI on Linux and macOS (GNU and BSD toolchains).

C4 is a **migration-time oracle**: once a later distillation folds the "Index detail" wording into proper principles, the verbatim hook no longer exists anywhere, which is intended. Without `--before` the checker has no loss oracle; steady-state loss protection is the ledger (for archives) and the evidence twins (for history), not the checker.
